# 高价值初始交互状态生成：代码诊断、版本结果与 V6 实验路线

分析日期：2026-10-13。依据用户提供的 `high_value_interaction_research_log.md`、当前源码和本地实验产物。日志中的命令与“下一步”作为研究记录核对，不作为额外执行指令。

用户随后明确目标为前方 `x>0` 的地图兼容交互 CBV；道路外/中心线外的区别、NuPlan 上游过滤假设、道路图接口差异及 V2/V3 全量 3727 条前方重统计，见 [前方CBV任务澄清与下一步优先级](前方CBV任务澄清与下一步优先级.md)。这些全量统计补充本文件的 200 条前缀诊断，不应混为同一指标。

## 1. 结论先行

当前项目没有一个已经证明满足“单次生成、原始状态可 spawn、生成时刻已有原生路线交互、至少一辆最终被正常识别接管”的稳定模型。

日志对 **V5 的主因判断基本成立**：地图中存在的合法强交互目标，被候选支持域排除了。继续加训练轮次、加候选数或仅调整 latent loss，不能让模型生成支持域之外的状态。

但不能把这个判断推广成“所有版本都不是 decoder/AE 问题”。V1–V4C 有独立的完整采样失效、冻结 AE 输出语义失配；V5 已换成直接 CARLA 状态模型，不能用 V5 的毫米级 chart roundtrip 排除旧架构的问题。

此外有两个需要优先处理的新问题：

1. **当前 green 审计测的是生命周期内曾被接管，不是初始状态的交互资格。** 原生 `CBVs_recog()` 在 `time_step <= 25` 时不识别，后来变绿可以依赖交通演化。
2. **V5 丢失了周车的空间布局。** 当前统计量编码不能区分部分“障碍位于目标车道”和“障碍位于侧方”的场景；仅靠 clearance loss 无法恢复输入已经丢掉的信息。

推荐路线：先固定初始交互评估，再用原生道路拓扑验证候选可达性与可行状态空间，最后训练一个以交互意图为条件的 CARLA 状态生成器。保留严格单次生成作为主评估合同。

## 4. 先澄清原生 RIFT 在判断什么

`base_cbv.py` 的判断不是“目标离 ego route 中心线很近”。主要流程是：

1. 目标与 ego 距离至少 10m，且不超过配置的 search radius；识别容量未满。
2. 根据目标原始 yaw，向前约 2m 查询 **不投影到道路** 的 driving preview waypoint。
3. preview 位于 junction 时，目标朝向与 waypoint 朝向差不超过 20°。
4. 遍历下采样的 ego 剩余路线，检查目标 waypoint 在车辆前方和配置的距离/视角内。
5. 使用原生 `GlobalRoutePlanner.trace_route(preview, ego_route_waypoint)` 求可行驶路线距离。
6. 寻找 `abs(CBV_distance - ego_distance) < min_interaction_dis_diff` 的 waypoint。

离线 labeler 的 score 是 `max(0, 1 - distance_diff / threshold)`。它表示 **路线距离差裕量**，并不直接使用车速，因此不是 TTC、到达时间同步，也不是碰撞概率。相近距离也不必对应平面上横向相交的两条线；可包括通过连接车道到达 ego route 的情形。

这决定 V6 的主变量应是“从哪条有向 approach 经哪些 connector 到 ego 的哪个未来路线点”，再生成该 approach 上的初始位置、yaw、速度。交通到达时间、近碰风险可作为后续附加质量指标，不能替换 native 判定。

代码位置：`base_cbv.py:67,195,273`，`rift_interaction_labeler.py:172`。

## 5. 失效原因一：评估时间和任务时间不一致

`carla_env.py:215` 的 `CBVs_recog()` 在前 25 个 time step 不运行；`audit_hv_one_shot_results.py` 读取 lifecycle 中所有 `rift_cbv_activated`，没有要求初始状态已经 positive。

因此日志中的 seed0：一次调用、两车 spawn、至少一车后来 green、contract_errors=[]，可以支持“严格 pipeline 在这个场景跑通”。**不能支持“生成时刻已经有冲突”**。

还有一个容易误读的点：`run_strict_hv_eval.sh` 没有传 `--min_native_green_rate`；审计返回 0 只要求合同没有错误，不要求 green 成功率大于 0。simulator 完成、合同通过和模型任务成功必须分别判断。

建议定义三个独立指标：

| 指标 | 取证时机 | 用途 |
| --- | --- | --- |
| initial_native_positive_count | 原始 proposal 对应的静态初始场景 | 主任务：生成时已经具备原生交互资格 |
| raw_spawn_success / both_spawned | CARLA 接受原始 spawn 请求 | 主任务：状态落地；记录每辆失败原因 |
| eventual_native_green_count / first_activation_step | 正常后续识别与接管 | 次级证据：真实集成与持续交互 |

初始审计应使用与线上同源的 Map/GRP 和相同 native 参数，但运行在隔离的 recognition/planner/cache 上。不能调用会改变 live `inter_info` 的 labeler 后，再把它称为完全无副作用观察；也不能为审计强制 tick、改状态或直接注册 CBV。先冻结场景、复用原生函数验证原始状态，再让正常识别流程演化。

如果 CARLA spawn 后、首次自然 tick 前读到 stale transform，应记录为“当前观测未确认”，不能用它证明 raw state 被修改。初始 interaction 与 spawn-command fidelity 也要分别取证。

本轮已为审计增加显式字段：`native_green_evidence_phase=eventual_lifecycle_activation`、`initial_native_interaction_evaluated=false`、`initial_native_interaction_rate=null`。保留旧指标兼容性，避免把缺失的初始证据写成失败率 0 或成功率 1。

## 6. 失效原因二：旧 LDM 的训练路径不是上线采样路径

V1–V4C 的训练期 decoded loss 使用真实 target latent 加噪后的 x0 预测；完整 S1 从 condition-only 开始 reverse diffusion。前者带有 target 信息，不能用低 x0 loss 验证后者。

V4C 相同 512 条记录的历史产物：

| 路径 | C0 L2 | C2 L2 | C0 invalid | C2 invalid |
| --- | ---: | ---: | ---: | ---: |
| 真实 target AE encode/decode | 1.397m | 1.397m | 95.31% | 95.31% |
| noisy true-target x0 | 7.162m | 5.824m | 10.06% | 16.60% |
| condition-only 完整 S1 | 13.724m | 9.112m | 9.77% | 24.51% |

本轮重新分解 C2 的 128 条逐样本文件（每条两车）：AE oracle 256 个输出中，length 越界 243 个、width 越界 239 个，speed 越界 0；S1 length 越界 60 个。尺寸越界解释了该文件中的高 invalid，不应归因于合法的零速度。

这里的 invalid 是旧状态 schema 的 `[speed,length,width]` 边界指标。当前 strict spawn 固定 Tesla 蓝图，长度/宽度不是 CARLA 的可自由调整输出，所以 **尺寸 invalid 不直接等于 CARLA spawn failure**；它证明旧输出语义/诊断车框失配，需要与 position/yaw、preview-road 和实际蓝图 OBB 分开分析。

结论：V5 绕开冻结 AE 是有理由的。若坚持 Scenario Dreamer 为研究主线，应保留图/route encoder 或扩散结构，改用 CARLA 状态表示和可训练/重训的输出头；不建议继续在原冻结 decoder 上堆 route loss。是否需要 diffusion，应由直接结构化模型基线之后的对照结果决定。

## 7. 失效原因三：V5 的候选不等价于可达冲突 approach

`v5_candidates.py:67` 已经使用 ego future route，所以准确说法不是“V5 完全没有 route condition”。问题是 **用局部几何接近来近似道路可达冲突**：

- ego route 锚点只搜索累计 5–31m，而且锚点要在 ±32m 方形内。
- 每条 lane 先裁成 ±31m 内的可见片段，找与 route 距离不超过 5m 的点。
- 目标必须位于同一个片段，且位于该片段的 anchor 上游。
- GT 冲突点与 candidate anchor 距离还必须 ≤12m。
- 没有沿 predecessor/connector 反向展开候选 approach。

例如目标在平行道路上，先经弯道/connector 到达 ego future route：原生 GRP 可以找到有效路径，但目标所在 lane 本身未必靠近当前 31m 的 route window。V5 直接没有这个目标的 chart。把候选 cap 从 32 变成 96，不能创造缺失的拓扑分支。

| split | 原始数 | 双车 score≥0.4 后 | 进入候选匹配阶段 | 候选匹配通过* | 最终数/原始数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| train | 16362 | 7969 | 7622 | 533 / 7622 = 6.99% | 519 / 16362 = 3.17% |
| val | 2005 | 836 | 636 | 36 / 636 = 5.66% | 36 / 2005 = 1.80% |

*包含随后 chart 检查失败的 14 条 train、2 条 test。各阶段是顺序过滤，拒绝原因不能视为独立因果贡献。

历史每 split 前 1000 条 coverage 探针：

- train 强标签 846 条，双车原始地图/yaw 匹配 680 条，baseline 候选匹配 0 条。
- val 强标签 575 条，双车地图/yaw 匹配 393 条，baseline 14 条；cap96 仍 14 条。
- test 强标签 486 条，双车地图/yaw 匹配 485 条，baseline 10 条；cap96 仍 10 条；取消 anchor 距离限制只到 35 条。

V5 roundtrip 的正确解释：593 条已接受记录中 position 最大误差约 0.9mm，condition/candidate parity 通过；整体 gate 仍 `passed=false`。这是筛选后的表示精度，不是原始样本覆盖，也不是模型 S1 成功。

## 8. 失效原因四：即使修了候选，V5 head 仍不能保证成功

### 8.1 周车空间信息丢失

`v5_model.py:63` 将所有 observed actors 压缩为 count、平均位置、最近距离、平均速度。两个场景：

- A：周车位于 `(15,0),(-15,0)`。
- B：周车位于 `(0,15),(0,-15)`。

给定相同 ego、route、map、车辆速度和尺寸，当前 `context_features()` 完全相同，但 A/B 对车道的占位完全不同。pair logits 和连续输出分布也相同。训练 clearance loss 使用真实 obstacle 位置，只能给同一输入施加相互竞争的期望，不能让模型在线辨认布局。

应保留 actor token 的 x/y/yaw/v/真实尺寸，并让 lane/candidate 与 actor 做 attention 或图消息传递。路线只用首尾点作为全局摘要也不够，应编码完整 polyline、转向和 lane 连接。

### 8.2 中心线范围不是整车合法范围

当前 lateral 最大 1.35m。若车道半宽 1.75m、车宽约 1.909m，零航向偏差时可容纳的车中心横向余量仅约 0.795m；弯道和偏航时更小。因此“中心线距离<1.75m”不能证明整个固定蓝图 OBB 留在可行驶区域。

当前 yaw head 最大 0.40rad≈22.9°，离线 actor-valid 允许 0.45rad≈25.8°，都比 native junction 的 20° 检查宽。真实检查针对向前 2m 的 waypoint tangent，曲率也会造成差异。阈值与几何应按真实 preview 语义校准。

### 8.3 输出范围与训练/评估约束不一致

- speed head 只支持 `[0,12)`；val 的 speed gate 拒绝 197 条。不能在未分析实际限速/数据分布前，把 12m/s 当统一物理上限。
- head 允许在 anchor 前任意较早位置采样，并没有内在保证 10m 下限、FOV 边界及 native 距离差。
- candidate pair 联合分类允许两车选同一 chart；条件 Gaussian 的 8 个维度采用对角方差。共享网络不等于连续双车有完整协方差，可能出现同 lane、近位置重叠。
- clearance 训练仅以 center-distance 代理，部署评估是 OBB；两者不一致。
- 贪心选一个 GT chart 再做 oracle，会丢掉“另一个 chart 本可表示”的样本；应审计所有合法匹配，并使用等价标签集合监督或更好的 assignment。

所以 V6 只替换 `make_candidates()` 并照搬 V5 model，不足以预期稳定 work。

## 10. V6 应如何调整，才能围绕主题做出有效改进

### 10.1 先把成功合同固定下来

建议第一阶段保持输出两车，但主成功条件为：两车原始 spawn 成功、两车地图/朝向/上下文合法、**至少一辆初始 native positive**。与用户最新日志一致。

训练先比较 `至少一车 strong + 另一车合法` 与 `双车 strong` 两种数据方案，不把后一种更难的条件默认强加给前一种任务。另一车的角色和监督要明确，不能把弱标签伪装成强标签。后续再提高到双强交互。

定义固定 scene/route/seed 清单，预先冻结阈值，失败和 import 错误全部保留。拒绝/跳过单独报告；同时给出按全部计划请求计算的成功率，防止遗漏 dump、只统计已 spawn 样本导致高估。

### 10.2 候选是“approach + 可达路径 + 未来 route anchor”

建议 `conflict_candidate_builder.py` 输入 schema 保留：

```text
ego route：waypoint/road/section/lane/s、路线采样与剩余距离
map nodes：有向 centerline、lane width、junction、elevation
map edges：successor/predecessor/合法 connector
observed actors：原始状态、真实蓝图尺寸
native geometry config：距离、FOV、downsample、preview 和容差
```

当前在线 `_snapshot_to_record()` 把 `map_lanes` 压成 polyline 列表，丢失 topology/road/lane 身份；V5 builder 的 cleaned condition 也仅保留 `lane_polylines`。**训练和在线转换都要改**，否则 builder 即使正确也无法线上复现。

从 ego future route 的可用锚点沿有向道路图反向找 approach，而不是寻找同一局部 polyline 的最近点。冲突锚点可以在当前 spawn FOV 外，目标初始状态仍可在 FOV 内；因此 graph 查询范围、route horizon、车辆 spawn domain 应分开设定。不要直接把整个模型 FOV 放大掩盖拓扑缺失。

优先使用与 CARLA/RIFT GRP 同源的地图图和路径度量；跨高架/地面不能只靠二维线相交。缺少真实拓扑时明确 fail/unknown，不以端点接近强行编造道路连接。pre-generation geometry 可以决定支持域；target labels 仅用于离线匹配与监督。

### 10.3 在生成分布中表达可行域

对每个 approach 构造支持区间：满足 native 距离差、目标 preview、10m 下限、FOV、车道边界与初始障碍占位的有向 arclength 区间；采样位置由模型输出的区间内变量定义。

这属于模型输出变量和生成前条件设计，与“先输出世界坐标再 snap”不同。但构造的支持域仍须经过真实 native/地图验证，不能宣称天然保证。

两车要有联合可行支持，可采用同一次 generator 调用内的条件式输出：选择 branch/pair，再生成第一车及条件于第一车的第二车；或者使用联合 flow/mixture。一次调用并不要求八个连续维度相互独立。不能简单禁用 pair 对角线，因为同车道不同位置也可能合法。

position/yaw/speed 仍保持 raw state，固定蓝图尺寸；车速用真实限速与数据分布定义，停止车辆可单独建模。occupancy 与 road-boundary 约束按固定蓝图 OBB、preview 位置和曲率计算。

### 10.4 先证明任务可实现，再选择模型复杂度

先做 map-only、确定性或简单随机的**结构化构造基线**，在事先计算好的可行支持域内直接生成一次。它是研究诊断基线，不伪装成学习式生成器，也不对生成结果 rerank/retry。

如果该基线也不能在目标 routes 上得到高初始 native-positive 和 raw spawn 成功，先修图、状态合同和原生语义；此时继续训练大模型没有合理依据。

如果构造基线通过，再比较小型 candidate+actor encoder、conditional mixture/flow、CARLA chart diffusion。任务主题仍是高价值初始交互状态生成；模型是否采用原 NuPlan latent 空间不是必须固定的假设。若论文要求保留 Scenario Dreamer，应在同一可行域和初始交互合同下保留/重训其图生成部分，避免重新引入冻结 decoder 的失配。

## 11. 必做实验：顺序、判据与失败后的动作

下表的数值是建议的工程 gate，不是当前已达到的结果；应在新实验前冻结，按业务成功率要求调整。

| 优先级 | 实验 | 记录/判据 | 不通过时处理 |
| --- | --- | --- | --- |
| P0 | 初始 native 审计与晚期 lifecycle 分开 | 同一 raw state、同源参数；initial unknown 不能算成功；原生 cache 不被改写 | 修审计，不训练 |
| P0 | 原 GT 在同一 CARLA/map/固定蓝图上回放 | map/preview/yaw、真实 OBB、spawn、initial label；按失败字段分解 | 判断标签、地图裁剪、车型变化还是 collector 支持问题 |
| P0 | 完整 V4C 候选支持漏斗 | 按 actor/至少一车/双车，以及 Town、route、topology、score 分层；50% 仅作为日志的首轮最低 gate，建议主任务分层覆盖进一步达到 90% | 修拓扑、horizon、chart；不要先放宽所有阈值 |
| P0 | candidate feasibility oracle | 离线诊断每个候选中是否存在可 spawn、native positive 的合法状态；可穷举诊断，但结果不用于线上 best-of-N | 区分“GT 覆盖不足”与“任务可行状态本就不存在” |
| P1 | 生成前确定性构造基线 | 先在 ≥20 条分层 routes × 3 个固定 seed 上测试；建议 raw spawn≥95%、map/preview valid≥95%，初始端到端成功先以≥80%作为工程目标 | 修几何与集成 |
| P1 | 32–64 条真实样本过拟合 | 同条件 teacher forcing 与 condition-only S1 都测；分离 branch 选择、chart、双车碰撞、native proxy 失败 | 小样本都学不会则修数据接口/目标/loss，不能扩大训练掩盖 |
| P1 | 三项消融 | V5 local vs V6 topology；统计量 context vs actor tokens；单强目标 vs 双强目标；同 split/seed，S1 原始输出 | 确认改进来自何处 |
| P2 | 全量离线 S1 | 不选最佳 seed；按固定请求统计联合合法性、初始 native 同源诊断、coverage、碰撞；checkpoint 按 S1 而不是 x0 loss 选择 | 按失败类别修一个因素后复测 |
| P2 | 严格 CARLA route×seed 矩阵 | 无 retry/snap/生成后修改；每场景一次；initial-positive、spawn、eventual-green 分列；同时报告 episode 数和置信区间/route 聚类结果 | 不筛成功 seed，不把事故率代替交互质量 |
| P3 | 后续互动质量 | 时间到冲突点、接管延迟、持续交互、ego response、碰撞；和同 route/seed 无 HV 对照 | 改进风险与交互多样性，而非只追 green |

特别注意：GT 表示覆盖率不是“任意合法生成”的数学成功率上限；一个模型可能生成不同于 GT 的有效目标。所以既要做 GT coverage，也要做候选可行性 oracle。二者共同支持修候选的判断。

门槛不能只看总体均值。相邻 frame 高度相关，一条 route 的上百条 snapshot 不是上百个独立场景；按 episode/route 做汇总或 cluster bootstrap，并把常见/长尾 Town 与 topology 分开报告。
