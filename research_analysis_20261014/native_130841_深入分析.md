# native_headless_20261014_130841_599893 深入分析

本报告直接读取该批次 experiment 下 rows.jsonl、summary.json、analysis.json、输入 manifest、阶段日志和 server.log。额外统计由根目录 analyze_hv_completed_batch.py 生成，见 native_130841_deep_stats.json，其中记录了 V2/V3 native ledger 的 SHA256。

## 结论与证据边界

这次包含真实的模型效果问题，也包含审计实现问题。snapshot/native 阶段各完成 95 条，未汇总执行错误；spawn 阶段失效，不能当成生成输出全部不可落地。physics 默认未运行，attention 排序和最终 green 接管也未运行。

95 条来自原始分层选择的 100 条，排除了 5 条真实配对歧义；仅 15 个 episode block，Town04/11/12/13/15 各 12/5/28/28/22 条。它是诊断子集，不是完整 test 或 IID 95 次试验。

## 失败漏斗与版本比较

按互斥顺序“域外 -> preview 失败 -> native 失败 -> native 成功”统计：

|结果|V2|V3|
|---|---:|---:|
|域外|81|76|
|前方 preview 非 Driving|49|55|
|前方 preview 通过但 native 失败|43|30|
|前方 native 成功|17|29|

通过 preview 后的原生拒绝细分：V2 距离门限 9、junction_heading 7、no_interaction_waypoint 27；V3 分别 5、6、19。无 interaction waypoint 中，V2 10 个没有 route target 在其前向域内，17 个最小路线距离差>20m；V3 分别 5、14。

RIFT 原生代码比较的是沿可达路线的距离差 abs(CBV_distance-ego_distance)，并有距离和方位门限。它不是仅要求几何车道交叉，也不是已验证 TTC 或实际未来碰撞。一些失败的 best_distance_diff 约 490m，说明近距离位置也可能落在必须绕远的有向道路分支。具体例子：V3 record2335 的 best_distance_diff=495.7103m，record2371 为489.6257m。需学习“合法 approach、方向和到冲突点的距离”，只提供附近道路或 ego 车道中心线不够。

V3 场景成功率 29.47%，V2 17.89%，差 +11.58 个百分点。配对结果：共同成功6、仅V2成功11、仅V3成功22、共同失败56。15 个 episode block 的 bootstrap 95% 区间为 [0,26.37] 个百分点；不能据此声称已稳定显著优于 V2。

V3 的全体 center/preview Driving 分别103/190、106/190，低于V2的123/190、128/190。前方 preview 通过率也从60/109=55.05%降到59/114=51.75%；但通过 preview 后 native 成功从17/60=28.33%升到29/59=49.15%。V3 的收益来自交互兼容性改善，并未解决道路生成。

Town 的生成场景成功 V2/V3 为：Town04 0/3（12条）；Town11 0/0（5条）；Town12 5/4（28条）；Town13 6/16（28条）；Town15 6/5（22条）。提升主要在Town13，不是所有Town普遍改善。

原始池有前方正例的82场景，生成成功V2 16、V3 27；没有原始前方正例的13场景，两个模型各有1场景成功。不能把“saved pool无正例”当作无解证明，亦不能仅对82场景计算成功率后代表全部任务。

## 道路约束不能混为一个布尔值

中心 Driving、2m preview Driving、整车 footprint 包含、raw spawn 接受和原生交互是不同条件。GT record2376 actor573 的中心不在 Driving，但 preview 和 native 都通过；生成前方 native 中V2有1、V3有3个中心非Driving。增加中心硬门限后，结合 preview/native/2D占位，生成场景成功分别16/95和25/95。

因此 native candidate 不是道路合法性证明，但也不能把所有“中心不在lane”直接等同于整个状态非法。NuPlan预训练能输出道路外状态不构成任务可接受性的证据。本任务需要针对 lane、junction/可驾驶区域、高程和整车 footprint 给出明确验收口径。当前整车 polygon 的有效样本太少，不能给总体接受率。

本次 raw spawn 的 Town04 GT 自行车573被接受，但其采样道路 polygon 外面积约0.2766m²，总footprint约1.1378m²；自行车577完全包含。即使 GT 原始实车状态也未必满足“整车严格处于 Driving polygon”的硬条件。需要区分 GT 边缘状态、道路边界/连接处采样误差和真实越界；不能通过扩大所有地图边界来掩盖生成道路问题。

## 候选与 V6 approach 的缺口

使用历史 manifest 条件：原始前方 native positive119个，候选覆盖75/119=63.03%；选中前方正GT110个，覆盖70/110=63.64%。不能把候选集合直接当完整合法输出集合，否则会先删掉约36%的正GT。

pool_native 用 native_map_fallback_NOT_historical_model_input，覆盖50/119；不能与 manifest 的75/119解释成同一候选条件的效果变化。

V6 94/95场景有已知route roots与approaches，但110个前方正GT仅54覆盖，55未覆盖、1未知。V2/V3生成前方native正例覆盖7/17、9/29。代码make_condition从ego route lane roots沿predecessors反向搜索；这是“能在导出图中到ego route lane”的粗条件，不等价于完整RIFT route conflict。匹配又要求车道半宽内、heading误差<=0.38rad；道路交叉/转向和车头preview条件可能被漏掉。

这些数据只能证明当前覆盖测试召回不足，不能单凭聚合统计确定全部漏例都是拓扑漏边。下一步逐漏例分解：地图是否包含真实preview lane、是否有有向路线、冲突点是否进入导出范围、是否仅heading/宽度门限拒绝。以原生返回的交互点与target_route_to_interaction为离线oracle，校准覆盖，而不是用GT路线泄漏到推理输入。

actor tokens、宽度高程、有向连接、显式域目前是审计中构造的条件基础；不代表现有V2/V3权重已经消费它们。原checkpoint也没有因为审计记录output_domain就变成前方约束模型。

## spawn 失败根因与修复

pool_spawn 的首例record2325（Town04）尝试16个actor，ego与13个其他actor被拒绝，仅两辆自行车573/577被接受，随后两次destroy返回false。V2/V3的首例也在selected_gt cohort同样失败，尚未执行generated cohort。所以不是生成状态造成的清理失败，不能统计模型raw spawn成功率。

稀疏阶段首先读到残留车辆而报“世界非空”。进入Town11后地图重载清掉前Town残留，record155的ego+3个GT全部接受，随后四次destroy均false，再跳过余下82条。失败并不局限于自行车或Town04。

同步世界生成后零tick，Actor.destroy()先通过客户端最近帧缓存GetActorState，再决定是否发出删除RPC。新actor可能尚未进入帧状态。CARLA0.9.15官方源码可核验该路径：

- https://github.com/carla-simulator/carla/blob/0.9.15/LibCarla/source/carla/client/Actor.cpp
- https://github.com/carla-simulator/carla/blob/0.9.15/LibCarla/source/carla/client/detail/Simulator.h
- https://github.com/carla-simulator/carla/blob/0.9.15/LibCarla/source/carla/client/detail/EpisodeState.h

这是与观察高度一致的具体实现机制，但旧ledger未记录state cache和server删除RPC，无法事后证明每一次false都走了哪个分支。已将生产路径修为client.apply_batch_sync([carla.command.DestroyActor(owned_id)],False)，按本次创建ID删除且不tick；记录逐ID服务器响应，错误与缺响应仍中止。104项本地CPU测试通过，包含删除范围、零tick、不调用cached actor.destroy以及错误响应保留。服务器实跑尚未验证。

GT raw pose拒绝是另一问题。原始落地姿态z可接近0甚至为负，原位动态状态可存在，不代表用同一个姿态重新执行spawn碰撞检测必定成功。不能将所有GT raw spawn拒绝解释为原状态非法，更不能偷偷抬高z、重试后仍称raw通过。后续如做z提升，仅作为明确单独的初始化语义对照。

4. 修训练目标：先限定前方有效目标并明确槽位数量/无目标mask；对当前raw positive119 actor进行采样支持校准；保留个体actor tokens；区分有GT前方positive、未观测positive、拓扑未知、搜索未找到、证实无解。最后一类需要更强证据。
5. 分离地图/模型能力：GT teacher-forcing重建、已知合法lane/approach下生成、完整condition S1生成三组。GT重建失败先查AE/坐标/尺寸；oracle approach仍不work查解码和训练；oracle work、完整生成失败再查条件编码/approach选择。比较固定S1，不能增加重采样后仍与原S1当同口径比较。
6. 按Town/route/初始化frame/交通密度分层采集，保留episode拆分与歧义来源；先补Town11与高漏例道路结构，不盲目增加相邻帧。修完静态审计再独立恢复物理与最终attention/green测试。
